中文标题：Claude Code 动态工作流：多 Agent 自动调度
English Title: Claude Code Dynamic Workflow: Auto-Scheduling Multi-Agents

本期视频围绕 Claude Code 在 6 月推出的 dynamic workflow（动态工作流）展开，核心观点是：多 agent 系统已经从过去的"手动调度"演进为可由云端自动调度与编排的模式，从而把人从协调循环中解放出来。作者首先回顾旧的多 agent 实现方式：先与 AI 反复讨论生成 plan.md 或 to-do list，把任务拆成相对独立、分阶段的子任务写入文件，再通过 web 看板或开启多个终端，每个终端运行一个独立的 agent 实例（如 OpenCode、Codex）；当两个子任务可能同时修改同一文件而产生冲突时，则基于 git worktree 在文件系统层做隔离，从而最大化释放并行能力。但作者指出，这种方式在并行之前需要大量准备工作，运行后还要人工把结果回传给下一阶段 agent、反复调整 plan、处理合并冲突，human in loop 始终存在；当并发 agent 达到十几二十个时，逐个启动并把状态 merge 回主分支会非常耗时费力。

动态工作流（或称 ultra code）通过给每个 sub agent 开启 auto 自动模式、尽量授予全部权限，并由一个充当"包工头"的中心调度 agent（ultra/schedule）统一监督管理手下十几二十个 agent，来替代人工协调。其机理基于三个对外暴露的函数：agent（启动一个可选择是否文件系统隔离、并按任务复杂度选择 Opus、Sonnet 或 Haiku 等最划算模型的子 agent）、parallel（并行批量启动大量 agent）与 pipeline（流水线串行）；各 sub agent 的结果会自动归并进调度 agent 的上下文，无需人工搬运。除了去掉 human in loop，该架构还解决了几个关键问题：agent 偷懒（lazy，声称解决其实未解决）、自我偏差（self-bias，模型在同一上下文下审阅自己写的代码会偏向认为没问题），以及上下文过长导致前文丢失、智力下滑的问题——作者认为在 200K～400K 这样较短、干净的上下文区间，模型能力往往最佳，因此通过为每个 sub agent 维持尽量干净的上下文来提升表现。作者也提及 message bus 消息总线与 share state 共享状态等其他多 agent 协调模式。

随后作者给出一个具体实例：仅用一次 prompt，构建一个 RSS web 阅读器。系统自动将任务拆成规划、build 构建、verify 验证三个阶段、三层脚本，每层再分若干阶段，能并行则并行、需串行则串行。规划阶段并行设计前端、后端、前后端共享与整体架构，并专门引入一个对抗式 review agent 审核 plan 的合理性，再把所有结果归并以提升计划质量；构建阶段提前规划好每个 agent 只能改哪些文件，从而无需 git worktree 也能避免冲突；验证阶段同样采用对抗验证机制再次提质。整个 case 运行约一两个小时、用了十几二十个 sub agent，而现在用户只需与主 agent 交互即可。

视频也客观指出局限与隐忧：该架构对复杂分析性问题仍有能力上限；因上下文在不同 agent 间重复加载，token 成本比手动调度更高（但在国外厂商价格战下，千元以内已可体验）；过程被高度自动化、透明化后形成黑盒，对新手增加了不可见性，底层一旦出问题上层应用都会受牵连，带来信任风险。它也尚未解决多 agent 的异步消息转发问题，作者据此引出 message bus（消息队列）配合 share state 共享状态的去中心化架构，认为这去掉了中心协调者、更接近人类团队组织方式，可协作解决单个节点无法协调的超复杂任务，但也会带来路由出错难以异步调试、共享状态反复抢锁陷入恶性循环、空耗资源而状态无进展等新问题。最后作者总结从 2025 年单 agent 手动运行，到 2026 年上半年借价格战 token 变便宜而尝试 multi-agent，再到如今默认开启 dynamic workflow / auto coder 自动编排几十上百个 agent 的演进，并展望 agent 从能解决人类三四小时的任务，进一步发展到独立解决需要一两天乃至数年才能完成的超复杂任务，届时智能才算真正到来。
